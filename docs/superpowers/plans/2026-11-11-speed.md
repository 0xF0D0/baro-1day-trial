# Speed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring a full pass from about 35 minutes to about 5 by running brands side by side and shortening chosen waits, with a careful mode that restores the old pace.

**Architecture:** No new moving parts. Five collectors get smaller wait constants (four of them switchable back by one environment variable), `04_amazon` reads its settled cost once per brand, `angles.py` sends label requests through a small thread pool, and `run.py` plans one job per brand for every collector but one, with `--careful` planning the old way.

**Tech Stack:** Python 3 standard library, existing test suites (`unittest`).

**Spec:** `docs/superpowers/specs/2026-11-11-speed-design.md` (binding). It changes `docs/superpowers/specs/2026-11-11-run-all-design.md` section 3.

## Global Constraints

1. Hand-written code. At least one source is collected without a paid scraping service.
2. Rerun-safe. Running twice creates no duplicates. A missing item is marked ended, never deleted.
3. Honest gaps. A source that could not be reached is recorded as "could not look", never as "nothing found". Partial collection is marked.
4. Clean collection. No personal data of private individuals. Requests are spaced. A block is recorded, not worked around: nothing in this plan hides from a site's detection.
5. What a collector collects and what it writes (records, run result, statuses, reasons) does not change. Only waits and process layout change.
6. Inside one process a collector still sends its own requests one at a time.
7. Documents and code comments are in English. No absolute local paths, tokens or keys in any committed file.
8. Every task ends with its own suite green and these two green as well:
   `.venv/bin/python -m unittest discover -s part1/tests` and
   `TEST_DATABASE_URL=postgresql://localhost:5432/market_radar_test .venv/bin/python -m unittest discover -s part1/pipeline/tests`.
   A collector's suite runs with `.venv/bin/python -m unittest discover -s part1/collectors/<nn_name>/tests`.
9. No task runs a real collector, the real label command or `run.py` against the real collectors: the main session measures.

## Review Focus

1. With `RADAR_CAREFUL` set, the four site-facing waits are exactly the old values; without it, exactly the new ones (Task 1).
2. Amazon's reported `cost_usd` is the settled cost of all its runs, also when one run failed or never finished (Task 2).
3. Label lines are written in the order of the pending list and never twice, also when requests finish out of order (Task 3).
4. A rejected request or an authentication error during concurrent labeling stops the run and writes nothing after it (Task 3).
5. `--careful` plans exactly the old jobs and passes `RADAR_CAREFUL=1` to collectors only (Task 4).

### Task 2: Amazon reads its settled cost once

**Files:**
- Modify: `part1/collectors/04_amazon/source_collector.py`, `spec.md`, `tests/test_source_collector.py`

**Behaviour:** `POLL_S` becomes 3. `run_actor` no longer sleeps for `CHARGE_READ_DELAY_S`; it records the run's id and `finishedAt` and adds the cost it last saw. After the brand's last run (whatever the outcome: success, a failed run, an early return), one settling step waits until `CHARGE_READ_DELAY_S` after the latest `finishedAt` among the runs that ended, then reads each of those runs once and replaces its last-seen cost with `usageTotalUsd`; a read that fails keeps the last-seen value; a run that never ended keeps its last-seen value and is not read. `cost_usd` in the run result is the sum, as before.

- [ ] **Step 1: Write the failing tests** with the collector's HTTP function and `time.sleep` patched (follow how the existing tests fake `call`): three runs that end at known times with last-seen costs 0.01, 0.02, 0.03 and settled costs 0.06, 0.075, 0.63: the reported cost is 0.765; the settled values were read after the three runs, once each; the charge-delay sleep happened once (the only `time.sleep` call longer than `POLL_S`). A brand whose second run fails: the first two runs are still settled and the cost is their sum. A settle read that fails keeps the last-seen cost of that run.
- [ ] **Step 2: Run and see them fail.**
- [ ] **Step 3: Implement.** Keep `run_actor`'s return value; carry the run list in `st` (for example `st["runs"]`), and call the settling step from the one place that writes the brand's run result, so every exit path of `collect` is covered.
- [ ] **Step 4: Update `spec.md`:** `POLL_S` 3; step 4 of the run procedure says the cost is read once per brand after the last run, as above.
- [ ] **Step 5: Run the collector's suite and the two suites of Global Constraint 8; commit** (`Amazon: read the settled cost once per brand, poll every 3 s`).

### Task 3: Label requests eight at a time

**Files:**
- Modify: `part1/pipeline/angles.py`, `part1/pipeline/tests/test_angles.py`, `part1/pipeline/README.md` (one sentence in the Angles section)

**Interfaces:** `LABEL_WORKERS = 8`. `label_pending(conn, path, client, model, now, on_failure=None) -> tuple[int, int]` keeps its signature and return value.

**Behaviour (spec 2.4):** requests for the pending texts run in a thread pool of `LABEL_WORKERS`. The calling thread takes the answers in the order of the pending list and, for each, checks it and appends its line exactly as today. When taking an answer raises `anthropic.BadRequestError`, `AuthenticationError` or `PermissionDeniedError` (the errors that stop a run today), lines for the texts before it in the list have been written, nothing after it is written, requests not yet started are cancelled, and the exception propagates as today. `ask_model` is unchanged.

- [ ] **Step 1: Write the failing tests** (class `LabelTest`, with a thread-safe fake client):
  - eight pending texts, each fake answer taking 0.3 s: `label_pending` returns `(8, 0)` in under 1.5 s, and the file's lines are in the order of `pending(...)`;
  - answers that finish in reverse order (the first text's answer is the slowest): the file is still in pending order;
  - the fake raises `anthropic.BadRequestError` for the third of six texts: the exception propagates, the file holds exactly the first two lines, and the fake was not called for all six;
  - `LABEL_WORKERS` is 8 and no more than 8 requests are ever in flight (count in the fake).
- [ ] **Step 2: Run and see them fail.**
- [ ] **Step 3: Implement** with `concurrent.futures.ThreadPoolExecutor`; submit in pending order and take results in that order.
- [ ] **Step 4: README:** in the Angles section, say that `--label` sends up to 8 requests at a time.

### Task 4: `run.py`: every brand its own job, and `--careful`

**Files:**
- Modify: `part1/run.py`, `part1/tests/test_run.py`

**Interfaces:**

```python
BRAND_SEQUENTIAL = ("07_search_interest",)                      # one --all job in the normal plan
CAREFUL_BRAND_PARALLEL = ("02_tiktok_ad_library", "04_amazon", "06_google_results", "08_tiktok_posts", "09_tiktok_shop")
def plan_jobs(folders: list[str], brands: list[str], brand: str | None, careful: bool = False) -> list[Job]
def run_jobs(jobs, collectors_dir, log_dir, max_jobs, timeout_s, python=sys.executable, on_done=None, env=None) -> dict[Job, str]
```

- Normal plan: one job per brand for every folder not in `BRAND_SEQUENTIAL`; one `--all` job for those in it.
- Careful plan: one job per brand only for folders in `CAREFUL_BRAND_PARALLEL`; one `--all` job for every other folder (the plan before this change).
- With `--brand <slug>`, both plans give exactly one `--brand <slug>` job per folder.
- `--careful`: `main` uses the careful plan and starts the collectors with `RADAR_CAREFUL=1` added to their environment (`env` of `run_jobs`; `None` means inherit unchanged). The load and label commands are started without it. `BRAND_PARALLEL` is removed.
- `--jobs` defaults to 16.

### Task 5: Google ads keep 10 seconds and read a detail once a day (added during execution)

Task 1 had set `DETAIL_SPACING_S` to 2 for `01_google_ads_transparency`; that collector's finding F8 says page loads
3 seconds apart are refused with HTTP 429. This task puts the 10 seconds back, adds `DETAIL_REFRESH_HOURS = 24`
and `recent_details(brand_dir, start_epoch)` so that a detail fetched in the last 24 hours is not loaded again
(`detail_state` `skipped_recent`), and makes `BRAND_SEQUENTIAL` in `run.py`
`("01_google_ads_transparency", "07_search_interest")`. Spec 2.1, 2.2 and 2.5 of the design are the requirements.
